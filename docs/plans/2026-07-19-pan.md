# `pan` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the crop's x(t) a second, *declared* source — a constant-velocity
pan generated from two fractions of horizontal freedom — and make every consumer
that treats a route as evidence say so honestly when there is no route.

**Architecture:** `pan` is **not** a layout mode and **not** a hero kind (see
[the design](../specs/2026-07-19-pan-design.md) §1, §3). It is a new optional
`PanSpec` riding the existing authoring path
(`EDLEpisode → Manifest → ReframeSpec`). `reframe` gains a pure
`generate_pan_path` used *instead of* the route; `PathMeta` gains one `pan: bool`
recording which source produced the path; `check_episode` reads that bit and
reports `editorial-only` / `not-checked` instead of a circular pass;
`process_episode` skips tracking and the contradiction gate entirely.

**Tech Stack:** Python 3.13, dataclass config-specs, ffmpeg/ffprobe via
`scripts/lib/proc.py`, pytest. No new dependencies.

**Test-strength rule (carried from the fit-solid slice, which shipped nine
green-but-hollow tests):**

4. A test that asserts a *branch was taken* beats one that asserts an outcome the
   other branch also produces.

```python
@dataclass(frozen=True)
class PanSpec:
    """A generated, constant-velocity camera move (design 2026-07-19).

    `start`/`end` are fractions of the crop's AVAILABLE HORIZONTAL FREEDOM
    (`freedom = src_w - crop_w`), not of the source width: 0.0 puts the crop hard
    left, 1.0 hard right. Freedom is the right denominator because it is what
    actually exists to travel, and it is already the number the layouts model
    uses to decide whether a composition is controllable at all.

    DIRECTION IS THE SIGN of `end - start`. No direction vocabulary exists — that
    would be a second spelling for what the numbers already say, and this repo
    has just spent a slice deleting a name that duplicated a parameter
    (`fit-blur` -> `fit`).

    WIRE NAMES DIFFER FROM FIELD NAMES, uniquely in this repo: the JSON keys are
    `from`/`to`, because that is what reads correctly in an EDL, while `from` is
    a Python keyword and cannot be a field name. A `from_`-with-underscore field
    would leak that constraint into the wire contract. `from_dict`/`to_dict`
    carry the mapping, and it lives in exactly one place. Do not "fix" this.
    """
    start: float
    end: float

    def __post_init__(self) -> None:
        for name, v in (("start", self.start), ("end", self.end)):
            # bool BEFORE int: isinstance(True, int) is True, so {"from": true}
            # would otherwise silently mean 1.0
            if isinstance(v, bool) or not isinstance(v, (int, float)):
                raise ValueError(
                    f"PanSpec.{name} must be a number in [0.0, 1.0] — a fraction of the "
                    f"crop's horizontal freedom, where 0.0 is hard left and 1.0 hard "
                    f"right; got {v!r}")
            if not 0.0 <= float(v) <= 1.0:
                raise ValueError(
                    f"PanSpec.{name} must be within [0.0, 1.0] — a fraction of the crop's "
                    f"horizontal freedom, not a pixel offset; got {v!r}")
        if self.start == self.end:
            raise ValueError(
                f"PanSpec start and end are both {self.start!r} — a pan that does not move "
                "is not a pan. Drop the `pan` field entirely; a crop that holds still is "
                "already what omitting it gives you")

    def to_dict(self) -> dict:
        return {"from": self.start, "to": self.end}

    @classmethod
    def from_dict(cls, d: dict) -> "PanSpec":
        if not isinstance(d, dict):
            raise ValueError(
                f"PanSpec.from_dict: expected an object with 'from' and 'to' fractions, "
                f"got {type(d).__name__} — write pan as {{\"from\": 0.0, \"to\": 1.0}}")
        missing = [k for k in ("from", "to") if k not in d]
        if missing:
            raise ValueError(
                f"PanSpec.from_dict: missing {', '.join(missing)} — pan needs both "
                "'from' and 'to' as fractions of the crop's horizontal freedom")
        return cls(start=d["from"], end=d["to"])
```

- [x] **Step 1: Write the failing tests**

**This step's original fixture was impossible as written, and grew from 9 tests
to 14 across review.** `freedom=800, fps=10, dur=2` gives `n=20` → 19
intervals; `800/19` is not an integer, so `len(steps) == 1` cannot hold while
the endpoints stay exact (pigeonhole) — that draft could never have passed.
Shipped `freedom=760` (`19 × 40`, `steps == {40}`), plus a companion test at
`freedom=875` (the real, non-divisible case every actual episode hits) pinning
`max(steps) - min(steps) <= 1` instead of an exact single step size. Two
`round → int` mutations also survived the file as first written and needed
their own tests: truncation yields the *same* step multiset as rounding,
merely phase-shifted, so only comparison against the exact line (±0.5px)
catches it; and every other fixture had an integer `dur*fps`, so a 29.97fps
fixture was needed to see `round()` vs `int()` on the frame *count*. And the
"NO-SMOOTHING PROOF" test this step originally drafted **did not prove

```python
def generate_pan_path(pan: PanSpec, freedom: int, fps: float, dur: float,
                      max_speed: float) -> tuple[list[int], list[float]]:
    """A constant-velocity crop path with no route behind it (design 2026-07-19 §4).

    Returns (path, times) at the clip's own frame cadence — the same pair
    `reframe` otherwise derives from a tracked route, so `_xexpr` and
    `CropPath` are reached identically either way.

    IT DOES NOT SMOOTH, and that is a rule about provenance rather than shape.
    `pathsmooth.smooth` exists to tame OBSERVATION NOISE; a generated line has
    none, and running it through the smoother can only hurt in two ways — the
    rate limiter caps each per-frame delta and so silently prevents the pan from
    ever reaching `end` (the reveal the author asked for does not happen, and
    nothing in the report says so), while savgol fits a polynomial across the
    endpoints and bends a line that was already exactly right.

    Because the rate limiter is gone, the speed cap becomes a GATE instead of a
    silent correction (see the raise below). `max_speed` is reused as a CEILING,
    not a target: a cinematic reveal sits far below it, and its job here is to
    catch the absurd (a crop_scale typo turning a slow pan into a whip), not to
    express taste. No new threshold is invented.

    The pan spans the WHOLE episode by construction — there is no parameter for
    when it starts or stops, which is what makes dividing by `dur` correct below.
    Both degenerate inputs — no freedom to travel across, and no duration to
    travel during — are REFUSED rather than absorbed: each would otherwise
    produce a plausible-looking path that is not the move the author asked for.
    """
    if freedom <= 0:
        raise ValueError(
            f"a pan needs horizontal freedom and this layout has {freedom}px: the crop is "
            "as wide as the source, so the pan would clamp to a constant and render a "
            "STATIC frame — which looks like an ffmpeg bug, not a manifest one. Set "
            "crop_scale below 1.0, or pick a narrower crop_aspect")
    # Guards the division below. Without it dur=0 raises ZeroDivisionError, which
    # names neither the offending value nor a remedy, and a NEGATIVE dur is worse:
    # v comes out negative, slips under the max_speed ceiling untouched, and n
    # collapses to 2 — a silently truncated two-frame pan. Unreachable through
    # reframe today (_probe already refuses dur <= 0), but this is a public pure
    # function, and the freedom guard one line up would be arbitrary without its twin.
    if dur <= 0:
        raise ValueError(
            f"a pan needs a duration to travel across and this episode has {dur}s — "
            "a clip with no length has no room for a camera move. Check that the "
            "segment probes to a real duration, or drop the `pan` field")
    x0 = round(pan.start * freedom)
    x1 = round(pan.end * freedom)
    if x0 == x1:
        # PanSpec refuses start == end, but it validates FRACTIONS and cannot see
        # the freedom they get multiplied by. A span narrower than half a pixel
        # rounds both ends onto the same integer, and the render is then a static
        # frame the author never asked for — the same silent-static-frame failure
        # the freedom guard above exists to prevent, reached by a different road.
        raise ValueError(
            f"pan {pan.start}→{pan.end} spans {abs(pan.end - pan.start):.6g} of {freedom}px "
            f"of freedom, so both ends round to {x0}px — the render would be a STATIC "
            "frame. Widen the from→to span, or drop the `pan` field")
    v = abs(x1 - x0) / dur
    if v > max_speed:
        raise ValueError(
            f"pan {pan.start}→{pan.end} travels {abs(x1 - x0)}px across {dur:.3f}s = "
            f"{v:.0f} px/s, past max_speed {max_speed:.0f} px/s. Shrink the extent "
            f"(a smaller from→to span), give the episode a longer duration, or raise "
            f"max_speed if the whip is deliberate")
    # floored at 2 so the i/(n-1) denominator below can never be zero; a clip that
    # rounds to a single frame had no time to travel anyway, and two knots at the
    # same instant render as the constant that honestly describes it
    n = max(2, round(dur * fps))
    times = [i / fps for i in range(n)]
    # endpoints are EXACT: at i=0 the term is 0, at i=n-1 the ratio is exactly 1.0
    path = [round(x0 + (x1 - x0) * i / (n - 1)) for i in range(n)]
    return path, times
```
